# Локальная инвестиционная система — архитектурный план

**Статус:** концепция / зафиксированные продуктовые настройки  
**Дата:** 2026-10-24  
**Назначение:** персональная система исследования акций, проверки инвестиционных гипотез, принятия решений и учёта торговых результатов. Не автотрейдер.

## 1. Зафиксированные настройки (решено)

| Параметр | Значение | Следствие |
| --- | --- | --- |
| Среда выполнения | **Только локальный компьютер** | Ни VPS, ни публичный домен для MVP не нужны. |
| Основной AI-аналитик | **Codex CLI** | Кодекс запускается локально по запросу приложения. |
| Режим анализа | **`manual`** | Аналитика начинается только по явной команде пользователя, без автоматических ежедневных запусков. |
| Независимая проверка гипотез | **Включена** | До показа финальной рекомендации обязательно проходит второй этап критической оценки. |
| Дополнительные провайдеры | Claude Code CLI; LLMost как возможный резерв | Не обязательны для первой версии. |
| Стратегии | Swing (дни) и Position (недели/месяцы) | Раздельные правила, сигналы и результаты; общий контроль риска портфеля. |
| Данные | PostgreSQL + pgvector | История котировок, решений, исследований, текстов, эмбеддингов и фактических исходов. |
| Брокер | Finam Trade API | Рыночные данные и, позже, заявки через изолированный модуль приложения. |
| Торговое действие | **Только после отдельного подтверждения человеком** | Ни главный агент, ни подагенты не вызывают торговые операции напрямую. |

### Значение `manual`

- Приложение может запускаться на `localhost` и позволять вручную обновить портфель/котировки.
- Никакой скрытой автоматической AI-аналитики при старте, по таймеру или по входящим котировкам.
- Кнопки типа «Проанализировать рынок», «Проверить гипотезу», «Оценить портфель», «Разобрать итоги» инициируют конкретные задачи.
- Если компьютер выключен, система ничего не анализирует, не уведомляет и не исполняет локальные команды.
- Возобновление после офлайна: при открытии приложения пользователь может запросить синхронизацию заявок/исполнений, затем отдельно запустить анализ.

## 2. Рекомендуемый стек и границы компонентов

- **Frontend:** Nuxt 4 + Nuxt UI.
- **Backend:** Nitro / TypeScript, Bun как runtime и менеджер пакетов.
- **Хранилище:** PostgreSQL, pgvector, Drizzle ORM.
- **Сбор и расчёты:** типизированные адаптеры Finam; индикаторы, риск-метрики и результативность вычисляются кодом, не LLM.
- **AI-оркестрация:** локальный `codex exec` как основной провайдер; нативные *custom subagents* Codex для узких ролей; вторичная возможность `claude -p` и LLMost для независимой проверки / fallback.
- **Векторизация текстов:** отдельно выбранная модель эмбеддингов (локальная по возможности либо через API), независимо от выбора модели аналитика; pgvector сам эмбеддинги не строит.
- **Доступ:** `127.0.0.1`, никакой публичной экспозиции и необходимости системного сервиса 24/7.

```text
Браузер → Nuxt UI
            │
            ▼
       Nitro / Bun
        ├── Research service ──► Codex CLI (корневой аналитик)
        │                          ├── market_researcher
        │                          ├── hypothesis_critic
        │                          └── outcome_reviewer
        ├── Market data adapters ─► Finam + отчётность/новости
        ├── Hypothesis ledger ────► PostgreSQL + pgvector
        ├── Evaluation engine ────► статистика и бэктесты
        └── Trading gateway ─────► Finam Trade API (только после подтверждения в UI)
```

### Важное разделение

**Codex custom agents — средство разделения аналитических ролей, а не процесс исполнения ордеров и не база памяти.** Вся долговременная память живёт в PostgreSQL; перед каждой задачей приложение формирует контекст из свежих данных и релевантных исторических записей.

## 3. Локальные custom agents Codex

### Предпочтительная структура проекта

```text
investment-app/
├── .codex/
│   ├── config.toml
│   └── agents/
│       ├── market_researcher.toml
│       ├── hypothesis_critic.toml
│       └── outcome_reviewer.toml
├── AGENTS.md
├── server/
│   ├── adapters/finam/
│   ├── ai/
│   │   ├── codex-provider.ts
│   │   ├── claude-provider.ts
│   │   ├── analysis-orchestrator.ts
│   │   └── contracts/
│   ├── domain/
│   │   ├── hypotheses/
│   │   ├── risk/
│   │   └── evaluations/
│   └── trading/
├── db/
└── pages/
```

**Роли:**

1. **`market_researcher`** — исследование эмитента, рыночного контекста, первичных источников, факторов роста и риска. Выход: источники, наблюдения, аргументы *за* и *против*, пробелы данных. Не даёт распоряжений брокеру.
2. **`hypothesis_critic`** — критика конкретной гипотезы, проверка фактов и возражений, выявление утечки будущих данных, устаревших цифр, недоказанных предположений, проблем ликвидности. Выход: `supported | disputed | insufficient_evidence`, аргументация и недостающие проверки.
3. **`outcome_reviewer`** — разбор завершившихся или достигших горизонта гипотез; сравнение прогноза и факта, контрольные индексы, комиссии, просадка, контрфактический результат отклонённых идей. Не меняет автоматически стратегии.
4. **Корневой Codex-оркестратор** — принимает пользовательскую команду, запрашивает структурированные данные, делегирует независимые исследования, сравнивает выводы и формирует итоговый проект гипотезы.

### Пример `.codex/config.toml`

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 3
```

### Пример `.codex/agents/hypothesis_critic.toml`

```toml
name = "hypothesis_critic"
description = "Independent adversarial reviewer of investment hypotheses. Read-only."
developer_instructions = """
Read only the evidence packet and hypothesis-specific task you are given.
Look for falsifying evidence, stale or missing financial reports, liquidity concerns,
unsupported causal claims, data leakage, and inconsistent risk calculations.
Do not assume the initial thesis is correct.
Separate facts from inferences and cite provided sources.
Never place, modify, or cancel broker orders. Never access credentials.
Return a structured critique with an explicit evidence sufficiency verdict.
"""
```

**Подтверждено документацией Codex:** проектные роли можно описывать через `.codex/agents/*.toml`, у каждой нужны `name`, `description`, `developer_instructions`. Конфигурации подагентов наследуют права и MCP родительской сессии. Поэтому ограничение «read-only» в промпте **не является достаточной технической защитой**. Источники: https://learn.chatgpt.com/docs/agent-configuration/subagents и https://learn.chatgpt.com/docs/cli/reference.

### Обязательное правило независимой проверки

Второй аналитик получает **самостоятельный пакет исходных данных** и вопрос для оценки, **без финальной рекомендации и уверенности первого аналитика**, чтобы снизить эффект якоря. Затем оркестратор сравнивает выводы. В первой версии проверяющий может быть независимым подагентом Codex с отдельным контекстом; при наличии второго провайдера предпочтителен дополнительный cross-provider review через Claude. Два вызова одной модели — независимые по контексту, но не полностью независимые по ошибкам.

**Включённая проверка означает hard gate:** результат нельзя отметить «проверенной рекомендацией», пока critic не отработал успешно. При споре — статус `needs_review` / `insufficient_evidence`, а не автоматическое усреднение двух мнений.

## 4. Поток ручного исследования

1. Пользователь нажимает «Исследовать» и выбирает `Swing` / `Position` / обе стратегии.
2. Nitro создаёт `analysis_run` с ID, стратегией, временем, версией правил.
3. Сервис получает свежие цены, отчётность, новости и относит их к исходным источникам с отметкой времени; проверяет полноту.
4. Детерминированные функции рассчитывают показатели, ликвидность, максимальный допустимый риск, сценарии и примерные уровни входа/выхода.
5. Retrieval достаёт похожие старые гипотезы и их реальные исходы (без событий из будущего относительно анализируемого момента).
6. `market_researcher` готовит доказательства, корневой Codex формулирует гипотезу с условиями опровержения.
7. **Независимый `hypothesis_critic`** оценивает входные материалы самостоятельно, выявляет спорные места.
8. Код проверяет JSON Schema, источники, допустимые значения, свежесть данных, лимиты риска.
9. UI показывает карточку: идея, риски, горизонт, уровень уверенности, альтернативы, возражения critic, ссылки на источники.
10. Пользователь одобряет / отклоняет / откладывает **гипотезу**; это не размещает заявку.
11. Отдельное действие «Создать заявку» требует просмотра конкретного инструмента, направления, количества, цены, комиссии и явного подтверждения.
12. В БД сохраняются все версии, исходный evidence snapshot, комментарий пользователя и результат по истечении горизонта.

### Контракт результата

Минимальные поля: `run_id`, `instrument_id`, `strategy`, `horizon`, `thesis`, `supporting_evidence[]`, `counter_evidence[]`, `assumptions[]`, `invalidation_conditions[]`, `entry_scenario`, `exit_scenario`, `risk_notes[]`, `sources[]`, `evidence_timestamp`, `critic_verdict`, `critic_findings[]`, `status`.

Рекомендуемые состояния: `draft`, `awaiting_critic`, `needs_review`, `ready_for_user`, `user_approved`, `user_rejected`, `watching`, `closed`, `evaluated`.

## 5. Память, обратная связь и развитие

**Не путать:**

- **SQL-память:** сделки, истории цен, решения, количественные показатели и результаты.
- **Векторная память:** поиск похожих описаний ситуаций, новостей, аналитических отчётов и выводов.
- **Обучение процесса:** отдельная статистическая система оценки по стратегиям, выборкам и версиям правил.

Главная сущность — `hypothesis`: *что ожидаем, почему, при каких наблюдаемых условиях откажемся от идеи и когда проверяем результат*.

- Неизменяемый снимок аргументов и времени их доступности при создании идеи.
- Отдельные оценки: предпочтение пользователя, фактический исход на горизонте, качество аналитики относительно бенчмарка.
- Учёт **отклонённых** гипотез: для них тоже рассчитывается гипотетический исход, но без фиктивного исполнения/ликвидности.
- Ретроспективы должны включать комиссии, спред, возможное проскальзывание, худшую просадку и сравнение с индексом/кэш-позицией.
- Поправки стратегий предлагаются пользователю как версии; не переписывают прошлые рекомендации задним числом.
- Для оценки изменений использовать walk-forward / out-of-sample, а не оптимизацию на всей известной истории.

### Черновой набор таблиц

`instruments`, `candles`, `market_events`, `issuer_reports`, `documents`, `document_embeddings`, `strategies`, `strategy_versions`, `analysis_runs`, `hypotheses`, `hypothesis_reviews`, `hypothesis_events`, `hypothesis_evaluations`, `accounts`, `portfolio_snapshots`, `orders`, `executions`, `source_snapshots`.

Историю котировок и числовые поля не хранить **только** в виде эмбеддингов: численные сравнения и бэктест должны работать на типизированных данных.

## 6. Торговый контур и безопасность

- Доступ к Finam разделить на **market read-only** и **trade write**. Если API-токен брокера совмещает полномочия, обеспечить разделение хотя бы на уровне отдельного локального процесса/адаптера, переменных окружения и прав файлов.
- Кодекс не получает торговых секретов, директории с ними, прямых MCP-инструментов `place_order`, `cancel_order`, неограниченного shell-доступа к торговому gateway.
- Роли из TOML наследуют права и MCP родителя: техническую изоляцию реализовать **вокруг процесса**, а не рассчитывать на инструкцию «не торгуй».
- Выделить отдельный процесс/модуль размещения заявок вне агентского sandbox, только с командой от UI и повторной авторизованной валидацией.
- На уровне кода: ограничения размера позиции, дневного убытка, суммарной экспозиции, концентрации по секторам, допустимой ликвидности; все пороги конфигурируемые.
- Первоначально: paper trading, без кредитного плеча и автоматического live-исполнения.
- Учитывать биржевые расписания, вечерние/выходные торги там, где они доступны, остановки торгов и ценовые разрывы. Локальная система выключена вместе с компьютером.
- Для операций брокера: идентификаторы заявок, идемпотентность на стороне приложения, учёт неясных исходов после тайм-аута, сверка состояния с Finam перед повтором.
- Брокерские стоп-заявки могут помогать при выключенном ПК, но не гарантируют цену исполнения.
- Не доверять инструкциям внутри новостных статей и документов; содержимое источников — **данные**, не управляющие команды для агента.

## 7. Порядок реализации

### Фаза A — фундамент

- Nuxt UI + Nitro/Bun + PostgreSQL + Drizzle + pgvector.
- Локальная конфигурация, миграции и безопасное хранение токенов.
- Finam read-only: инструменты, котировки, портфель, история.
- `AGENTS.md`, Codex CLI adapter, проверка доступности CLI и структурированный результат.

### Фаза B — исследовательский цикл

- Ручной запуск исследований.
- `market_researcher` + `hypothesis_critic` и обязательная независимая критика.
- Карточка гипотезы, источники, версия аналитики, сохранение решений.
- Swing и Position как независимые стратегии.

### Фаза C — память и оценка

- pgvector retrieval для прошлых ситуаций.
- Виртуальные позиции и историческая оценка гипотез.
- `outcome_reviewer`, сравнение с базовыми стратегиями и режим `why_not_buy`.

### Фаза D — торговые функции

- Интеграция с демосчётом / paper trading.
- Торговый gateway с явным подтверждением в UI, сверкой с брокером, защитой от дублирования.
- Реальные заявки — только после проверки контроля рисков и длительной оценки качества рекомендаций.

## 8. Открытые технические решения (не считать согласованными)

- Какие российские рынки, инструменты и тарифы реально доступны конкретному счёту Finam.
- Источник отчётности и юридических/новостных событий; качество, лицензии и ограничения API.
- Конкретная модель эмбеддингов и возможность полностью локальной генерации векторов.
- Поддерживаемая локально версия Codex CLI и её режим multi-agent; интерфейс запуска из Bun.
- Кому поручать second opinion по умолчанию: отдельный Codex critic или Claude CLI как иной провайдер.
- Численные лимиты риска, комиссии, горизонт проверки, капитал и доступность демосчёта.

> **Зафиксированное решение:** локальный Nuxt-продукт с основным аналитиком **Codex**, режимом **manual** и обязательной **независимой проверкой каждой гипотезы**. Нативные локальные Codex subagents — выбранный кандидат для специализации ролей; торговые права никогда не передаются агентской команде.
