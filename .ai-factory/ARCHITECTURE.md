# Архитектура IIS

## Обзор и обоснование

IIS — единое Nuxt-приложение с чистым функциональным доменом, сервисами сценариев и адаптерами
внешних систем. Документ фиксирует существующую структуру технических слоёв; он не требует
переноса файлов, введения репозиториев или преобразования функций в классы.

Такое разделение сохраняет вычисления воспроизводимыми и позволяет проверять инвестиционные
инварианты без БД, HTTP и запуска LLM. PostgreSQL, Redis, процессы агентов и HTTP находятся
за пределами чистого домена. Отдельный BullMQ-воркер выполняет служебные задачи.

Основания: TypeScript strict, Nuxt 4/Nitro, Drizzle через NuxtHub DB, персональное использование,
ручное исследование и paper trading. Требования и решения — в
[исходном плане](../INVESTMENT_ARCHITECTURE_PLAN.md) и
[плане реализации](../IMPLEMENTATION_PLAN.md).

## Структура

```text
app/                      страницы, UI-компоненты, composables и клиентские утилиты
shared/                   типы и zod-контракты для клиента и сервера
server/
  api/                    HTTP, аутентификация и валидация входных данных
  services/               сценарии, запросы Drizzle, сбор пакетов и сохранение результатов
  domain/                 чистые вычисления и правила
    market/               индикаторы и календарь
    strategies/           правила и детерминированный сигнал
    risk/                 ограничения риска
    hypotheses/           проверка гипотез и переходы состояний
    evaluations/          исходы, бэктест и walk-forward
    memory/               подготовка и отбор памяти
  ai/                     контракты, провайдеры и изоляция процессов агентов
  adapters/market/        интерфейс рыночных данных, Finam и mock
  trading/                paper-брокер и жизненный цикл заявок
  db/schema/              Drizzle-схемы
  db/migrations/          сгенерированные SQL-миграции
  plugins/                инфраструктура и lifecycle приложения
  utils/                  серверные хелперы, auth и выбор провайдеров
workers/                  BullMQ без виртуальных импортов Nuxt
tests/                    Vitest для домена, агентов и служебных задач
deploy/                   Ubuntu: Bun, systemd, Nginx
```

## Направления зависимостей

- `app` использует `shared` и HTTP API; не импортирует серверные сервисы, БД и секреты.
- `server/api` вызывает сервисы или paper-брокер после серверной проверки пользователя и ввода.
- `server/services` связывает Drizzle, доменные функции, провайдеры AI и рыночных данных.
  В текущем проекте доступ к БД находится прямо в сервисах; отдельного слоя репозиториев нет.
- `server/domain` зависит от чистых типов и функций, включая `shared`; не импортирует Nuxt/Nitro,
  Drizzle-клиент, Redis, сервисы и HTTP-клиенты.
- `server/ai` реализует `AgentProvider`; `server/adapters/market` реализует `MarketDataProvider`.
  Провайдеры не заменяют вычисления и проверку бизнес-правил текстовыми ответами.
- `server/trading/paper-broker.ts` владеет изменением заявок и использует доменные проверки риска.
- `workers` использует обычные TypeScript-импорты и собственную инфраструктуру соединений;
  request-scoped хелперы и виртуальные алиасы Nuxt здесь недоступны.

## Взаимодействие слоёв

Исследование начинается явным действием пользователя: API → `services/analysis.ts` → пакет данных
на выбранную дату → роли агентов → кодовая проверка → `gateStatus` → сохранение результата.
`hypothesis_critic` получает независимый контекст без уверенности и рекомендации аналитика.
Только успешный поддерживающий вердикт вместе с пройденной кодовой валидацией даёт `ready_for_user`.
При сбое критика результат остаётся в `awaiting_critic`.

Paper-заявка проходит создание с проверкой риска, затем отдельное явное подтверждение пользователя
с повторной проверкой. Реального исполнения у брокера нет. Одобрение исследовательской гипотезы
не заменяет подтверждение заявки.

Изменение правил создаёт новую `strategy_versions` со статусом `proposed`. Активация — действие
пользователя. Прошлые гипотезы сохраняют ссылку на использованную версию.

## Обязательные инварианты

1. Режим исследования — `manual`: AI-анализ не запускается таймерами, очередями, startup hooks
   или поступлением рыночных данных.
2. Индикаторы, уровни, размер позиции и исходы считает доменный код. LLM формулирует тезисы
   и возражения в рамках проверяемых JSON-контрактов.
3. Данные и retrieval ограничиваются `as_of`: `available_at`/`published_at` не позже этой даты.
   Параметры калибруются только на in-sample; out-of-sample служит независимой проверкой.
4. Источники, новости, отчёты и память — недоверенные данные, а не инструкции для агента.
5. Агенты запускаются через `server/ai/*-provider.ts`, в изолированной временной директории,
   с белым списком `agentEnv()`. Codex использует read-only sandbox и отключает пользовательские
   конфиги и правила. Секреты брокера, БД, Redis и авторизации в окружение агента не передаются.
6. API защищается на сервере; middleware страниц не заменяет `requireUser`. Персональные ответы
   не попадают в глобальный кэш.
7. Redis cache и durable state разделены. Для сессий и очередей нужен `noeviction`.
8. Bun остаётся пакетным менеджером и production runtime (`nitro.preset = 'bun'`). Docker Compose
   используется для локальной инфраструктуры; production — Bun + systemd + Nginx.

## Примеры из проекта

Тонкий HTTP-хендлер — `server/api/hypotheses/[id]/decision.post.ts`:

```ts
import { hypothesisDecisionInput } from '../../../../shared/schemas/investment'
import { decideHypothesis } from '../../../services/hypotheses'

export default defineEventHandler(async (event) => {
  await requireUser(event)
  const id = uuidParam(event)
  const { action, comment } = await readValidatedBody(event, hypothesisDecisionInput.parse)
  return decideHypothesis(id, action, comment)
})
```

Доменная проверка не требует инфраструктуры (`server/domain/hypotheses/state.ts`):

```ts
import { gateStatus } from './server/domain/hypotheses/state'

const status = gateStatus({
  criticVerdict: 'supported',
  criticSucceeded: true,
  validationOk: true,
})
// status === 'ready_for_user'
```

## Работа с существующим кодом

Следуйте текущим границам при добавлении функциональности. Не переписывайте соседние модули ради
формального соответствия другому архитектурному шаблону. Новые обёртки и уровни вводите только
при конкретной потребности; сначала используйте существующие хелперы и интерфейсы.

Схемы БД меняются через `nuxt db generate` с проверкой и коммитом SQL. Генерация миграций
в production запрещена. Справочные навыки ORM не переопределяют этот процесс.

## Проверки и нежелательные решения

После изменений выполняйте `bun run typecheck`, `bun run typecheck:worker`, `bun run test`,
`bun run lint`, `bun run build`. UI дополнительно проверяйте в реальном браузере, когда это возможно.
Mock-проверки не доказывают качество стратегий на реальном рынке или доступность внешних провайдеров.

Не переносите расчёты в LLM, не обходите критика, не меняйте активную версию на месте,
не выдавайте агентам доступ к `server/trading/**` и не добавляйте автоматическое исполнение заявок.
Не подключайте серверные секреты или клиенты БД в `shared` и клиентский bundle.
