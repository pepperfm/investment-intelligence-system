# Базовые правила проекта

> Соглашения, выявленные анализом кодовой базы. Редактируйте по мере необходимости.

## Соглашения об именовании

- Файлы серверного кода и утилит: kebab-case (`paper-broker.ts`, `codex-provider.ts`); короткие модули — одно слово (`market.ts`, `format.ts`).
- Маршруты Nitro: `<имя>.<метод>.ts`, динамические сегменты — `[id]`, `[strategy]` (`server/api/hypotheses/[id]/decision.post.ts`).
- Vue-компоненты: PascalCase, обязательно из нескольких слов (`DeltaValue.vue`, `PriceChart.vue`); лежат в корне `app/components/` (подкаталоги дают префикс имени).
- Композаблы: `useXxx.ts` в `app/composables/`.
- Переменные и функции: camelCase; константы-справочники: UPPER_SNAKE (`DEFAULT_RULES`, `STRATEGY_IDS`, `STATUS_LABELS`).
- Типы и интерфейсы: PascalCase (`StrategyRules`, `EvidencePacket`); zod-схемы — camelCase с суффиксом `Schema`/`Input` (`criticOutputSchema`, `startRunInput`).
- Колонки БД: snake_case в SQL, camelCase в Drizzle-схеме.
- Тексты для пользователя — на русском; комментарии в коде и идентификаторы — на английском.

## Структура модулей

- `server/domain/**` — чистые функции (индикаторы, правила, риск, оценка, валидация, состояния гипотез, память); без импортов Nuxt/Nitro и БД.
- `server/services/**` — работа с БД и оркестрация (анализ, рынок, память, оценки, стратегии, настройки).
- `server/api/**` — тонкие хендлеры: `requireUser` → `readValidatedBody`/`getValidatedQuery` (zod) → сервис.
- `server/ai/**` — провайдеры агентов, изоляция процессов, контракты и строгие JSON-схемы.
- `server/adapters/market/**` — провайдеры рыночных данных за интерфейсом `MarketDataProvider` (только чтение).
- `server/trading/**` — единственное место изменения состояния заявок (paper-брокер).
- `shared/` — общие типы и zod-схемы клиента и сервера.
- `app/` — страницы, компоненты, композаблы, утилиты UI; данные — через `useFetch`/`$fetch` к `/api/**`.
- `workers/` — обычный TypeScript без Nuxt-алиасов.

## Обработка ошибок

- Сервер: `throw createError({ statusCode, statusMessage })` для ошибок, видимых клиенту; доменный код бросает обычный `Error`.
- Ввод API валидируется zod-схемами из `shared/schemas`.
- Вывод агентов проверяется zod; при несоответствии — `AgentOutputError`; сбой критика фиксируется событием, статус гипотезы не повышается.
- Клиент: мутации через `useAction().run(...)` — pending-состояние и toast об успехе или ошибке (`apiError`).

## Поток управления

- Предпочитайте плоский и читаемый поток управления вместо глубоко вложенных условий. Используйте guard clauses, ранние `return`/`continue`, небольшие именованные функции или явную классификацию, когда это упрощает код. Обрабатывайте граничные случаи и нерелевантные ветки в начале, чтобы основной путь оставался на виду.
- Все `if` — с фигурными скобками (`curly: all`), стиль скобок `1tbs`.

## Логирование

- Минимум `console.error` на сервере, без секретов и персональных данных.
- Ход анализа — в журнале запуска (`RunLogger` → `analysis_runs.log`); решения и переходы статусов — в `hypothesis_events`.

## Стиль кода

- Без точек с запятой, одинарные кавычки, отступ 2 пробела (ESLint stylistic; `bun run lint:fix`).
- Объекты от 3 свойств — многострочные, по одному свойству на строку.
- Во Vue-шаблонах — не больше 2 атрибутов в однострочном теге, иначе по одному на строку.
- Числа в UI — класс `.num` (моноширинные, табличные); цвета только семантические Nuxt UI (`text-muted`, `bg-elevated`, `text-success`).

## Тесты

- Vitest, файлы `tests/*.test.ts`, окружение `node`.
- Тестируются чистые модули (`server/domain`, `server/ai` без процессов, mock-адаптер); БД и Nitro в тестах не поднимаются.
